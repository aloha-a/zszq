# 限量产品预约抢购系统实施计划

**执行中**　｜　工期为两周，按 10 个工作日估算，从项目启动日计。工程框架进展见[过程记录](../../过程记录.md)。

项目目标是用 Java 打通活动管理、抢购下单和异步落单。在 10 万个瞬时请求争抢 1000 份额度时，要求不超卖、不少卖，绝大部分请求快速失败并得到明确提示。重复提交、服务重启和下游故障期间，每一份已扣额度都应能通过订单和库存流水核对。[题目原文，第 1–3 页](<../../../题目2：实现一个限量产品预约抢购系统 (1).pdf>)

## 一、先定业务口径

| 事项 | 拟定口径 | 对实现和验收的影响 |
|---|---|---|
| 活动与资格 | 活动支持创建、上线和下线，可配置总额度、单人限购数和开抢时间。受理前检查活动状态、时间、用户标识和购买份数。 | 对未开抢、已下线、超过限购、售罄和入口繁忙分别给出提示。 |
| 限购与重复提交 | 题目要求支持单人限购且重复提交只产生一笔有效订单。建议同一用户在同一活动只提交一笔有效申购，一单可买多份。 | 受理表对“活动 ID + 用户 ID”设唯一约束。相同份数重试返回原单号和状态，变更份数重提则提示已有申购。另设限购 3 份的用例，覆盖多份购买。 |
| 受理与成交 | 扣减额度和受理记录一起提交后，接口返回“已受理”和稳定的单号。消费者写入业务订单，下游确认后才标记“已确认”。 | 提供按活动和用户查原单的入口。即使活动已经售罄，丢失首次响应的用户也能查回结果。压测分别统计受理笔数和最终有效订单数。 |
| 失败与补偿 | 本地事务失败时整体回滚。下游超时或结果未知时保留已占额度，使用原单号核查、重试。确认业务失败且下游未生效后，才执行一次释放并记流水。 | 任一时刻，可售余量应等于初始额度减去累计扣减份数、再加上累计释放份数。同一单号的同一次扣减或释放最多记一次。 |

## 二、技术方案草案

以下选型用于估算工作量。题目指定 Java，数据库、消息队列和缓存产品可选。前端采用简单活动页，下游统一使用本地账户／TA 模拟服务。

| 决策 | 计划做法与取舍 |
|---|---|
| 服务与本地环境 | 拟用 Spring Boot、Maven、MySQL、RabbitMQ、JUnit 5 和 JMeter。活动、抢购、订单分别承担业务职责。压测时由网关向至少两个抢购实例分发请求，订单消费者和下游模拟服务可独立暂停或重启。 |
| 库存与恢复 | 以 MySQL 持久化余量为准。抢购事务内检查资格和余量，以带“余量足够”条件的更新原子扣减，同时写受理记录、库存流水和待发消息。该方案便于重启、对账，代价是热门活动的库存行可能出现锁等待，第 8 天用压测检验。活动展示信息可做短时缓存，活动变更后失效，交易在数据库复核，实例重启从持久化状态恢复。 |
| 削峰与降级 | 页面防止连续点击，网关限制突发流量。抢购入口设置有界并发和短队列，区分“繁忙，可重试”和“已售罄”。订单队列隔离下游。调用模拟服务设置超时、有限次数退避重试和熔断，下游持续变慢时自动暂缓调用，恢复后继续处理。 |
| 消息与一致性 | 拟采用本地事务加待发消息表。队列与消息均持久化，发布端在消息成功路由并获确认后标记已发，支持用原消息 ID 重投。消费端在同一事务写入业务订单和待调用下游的记录，提交后确认消息。下游按原单号幂等。旧消息不应回退订单状态，缺少前置状态的消息延后重试，超过上限进入死信队列供人工核查、重放。设计文档说明用本地事务与重投保障一致性的理由，并对比分布式事务方案。 |
| 表、接口与选型比较 | 定义活动、受理记录、业务订单、库存流水、待发消息的表结构与唯一约束。消息包含消息 ID、单号、活动 ID、用户 ID、份数和版本。接口覆盖活动管理、下单、查原单及本地下游调用。方案中比较 MySQL 与 PostgreSQL、RabbitMQ 与 RocketMQ，逐项写清并发扣减、事务消息支持、重复消费防护、部署运维成本，以及替换后涉及的 SQL 或消息收发改动。 |

## 三、两周排期

| 工作日 | 计划任务 | 当天的产出或完成标准 |
|---|---|---|
| 第 1 天 | 固定限购、幂等、成功与补偿口径。列出必测场景，建立过程记录。 | 形成业务规则和验收清单。开始保留实际使用的 AI 工具名称、Prompt 原文、输出和人工复核记录。 |
| 第 2 天 | 画组件图、抢购主链路时序图和数据流图。确定接口、表结构、消息格式和技术选型。 | 方案初稿含三张图和选型对比表。能沿图解释“已扣额度但消息尚未发出”以及“下游已成功但响应丢失”的处理方式。 |
| 第 3 天 | 建立 Java 工程与本地依赖，完成活动管理和最简活动页，接入双实例与本地模拟服务。 | 能创建、上线、下线同一活动，并从日志识别两个抢购实例。模拟服务能切换正常、延迟、失败模式。 |
| 第 4 天 | 先写库存扣减与幂等单元测试，再实现事务扣减、受理记录、库存流水和查原单接口。 | 验证最后一份被并发争抢、单次购买多份、余量不足和同一用户并发提交。失败事务不留扣减流水。 |
| 第 5 天 | 实现待发消息投递、队列消费、业务订单入库和下游调用，贯通正常流程。 | 一笔申购可用同一单号追踪到受理记录、扣减流水、业务订单和模拟下游结果。重复投递后仍只有一笔业务订单。 |
| 第 6 天 | 加入限流、排队、超时、退避重试、熔断、死信与人工重放。 | 下游超时后入口仍能响应。持续失败可进入死信，故障消除后以原单号恢复，能够区分重试次数和实际生效次数。 |
| 第 7 天 | 演练重复提交、响应丢失后重试、活动中途进程宕机重启。 | 三个场景各有一份独立日志或截图，可按单号核对订单和扣减，重启后继续销售剩余额度。 |
| 第 8 天 | 校验负载脚本与对账查询，逐级加压，再进行双实例 10 万请求突发测试。 | 留存实际发送时间窗、各实例请求数、QPS、拒绝原因、响应耗时、成功单数和库存余量。核对生成的负载是否达到目标。 |
| 第 9 天 | 演练队列积压、重复或乱序投递、持续消费失败和死信恢复。针对压测或故障演练中发现的问题复测。 | 留存积压增长与消退、死信内容、人工处置和最终对账结果。验证报告写入真实数据与复测差异。 |
| 第 10 天 | 按 README 从头复现启动、下单、压测与对账，完成文档和交付检查。 | 形成方案设计 PDF、源码及 README、验证报告、过程记录文档。记录实际环境、复现步骤及仍有的限制。 |

## 四、验收脚本和证据怎样准备

| 场景 | 测试输入与操作 | 通过条件和留证 |
|---|---|---|
| 库存与幂等单测 | 初始 1 份时两人并发各买 1 份。另测余量 2 份时申购 3 份，以及同一用户用不同请求 ID 重复提交。 | 第一组仅一人成功，第二组余量仍为 2，第三组只产生一笔受理与一次扣减。保存单测输出。 |
| 多实例突发抢购 | 新建 1000 份活动，准备 10 万个不同的合格测试用户，每人申购 1 份，下游正常。集中发起请求，等待队列和下游待处理任务清空。 | 预期有效订单 **1000 笔**、净扣减 **1000 份**、余量 **0**、重复有效订单 **0 笔**。保存压测原始数据、各实例流量、失败响应耗时分位数和数据库对账结果。10 万是请求规模，QPS 按实际到达量和时间窗计算。 |
| 重复提交与超时重试 | 分两组测试。一组让同一用户并发点击。另一组在受理事务提交后丢弃首次响应，让客户端带原身份重试。 | 两组分别留证。每组均返回或查回同一单号，只有一笔有效订单和一次扣减。 |
| 进程宕机与重启 | 在额度已扣、消息尚未发出时停止一个实例。另在订单已写入、消息尚未确认时停止消费者，然后重启并继续抢购。 | 比较重启前后余量、流水、订单和消息状态。已扣额度保留，待发消息能补发，重投消息不重复落单。 |
| 下游慢或不可用 | 让本地模拟服务延迟、停服，再恢复。另模拟下游已生效但响应丢失。 | 观察入口耗时、超时次数、自动降级及恢复过程。以单号核对下游实际生效次数，结果未知期间额度继续保留。 |
| 消息积压、乱序与死信 | 暂停消费形成积压再恢复。重新投递旧消息，另注入一条可持续触发消费失败的测试消息。 | 留存队列深度变化、旧消息未回退状态、有限重试后进入死信的记录。消除故障后人工重放，对账确认订单与额度一致。 |

压测前先记录机器配置、负载发生器和服务实例的部署位置。若发生器先达到上限，记录本轮实际发起量、到达量和发送时间窗，调整发压资源后复测。正常售罄、入口限流和系统异常分别统计，便于解释失败率。
